# План — fairytale-wanderings

Магазин подруги: каталог + заказы. Цель — убрать трение «напиши в личку и перечисли заказ руками»: клиент собирает заказ сам (сайт — гостевой checkout; тот же сайт открывается внутри Телеграма как Mini App — для удобства), заказ уходит владелице и сохраняется в БД.

Стек: Vue 3 (клиент) + Hono/Bun + PostgreSQL/Drizzle (сервер), docker-compose. Подробности по серверу — в `server/CLAUDE.md`.

## Готово ✅

- **Зависимости** обновлены до последних (Vue 3.5, Vite 8, ESLint 10, Hono 4.12, zod 4, TS 6 и т.д.). Mongoose оставлен на 8.x и затем убран при миграции.
- **Этап 1 — миграция БД Mongo → PostgreSQL + Drizzle.** Схема по файлам в `server/src/global/database/shema/` (products, users, orders, order_items + enum-ы). Пул и drizzle — в `DatabaseSingleton` (экспортирует `db`). Миграции через drizzle-kit (`server/drizzle/`). Compose переведён на postgres (порт на хосте — **15432**, наружу через `POSTGRES_PORT`).
- **Этап 2 — запись заказа в БД + письмо владелице.** У товара есть `stock`; при заказе остаток списывается атомарно (`stock >= qty`), при нехватке — `InsufficientStockError` (409, со списком всех недостающих позиций в `details.shortages`), нет товара — `ProductNotFoundError` (404). Ошибки `AppError` отдаются как JSON `{ error, code, details }`. Цена фиксируется из БД. Сохраняются имя и контакт. Гостевой checkout (без регистрации), `userId = null`. После успешной записи заказа владелице уходит письмо по SMTP (`nodemailer`, модуль `server/src/global/mail/`): состав, суммы, контакт, доставка. Креды в `.env` (`SMTP_`\*, `MAIL_FROM/TO`); если не заданы — письмо тихо пропускается, заказ всё равно создаётся.
- **Структура и конвенции** (см. `server/CLAUDE.md`): бизнес-логика — в роутах; `database/methods/` — только обращения к БД (импортируют `db` напрямую); ошибки — в `global/errors/` (`AppError` + наследники со `status`); единый обработчик — `middleware/errorHandler.ts` через `app.onError`. Роуты разложены по папкам (`routes/<name>/route.ts|validator.ts|helpers.ts`).
- **Seed**: 5 тестовых товаров с остатками (`bun run db:seed`).
- **Этап 3 — Telegram Mini App.** Сайт открывается внутри Телеграма как WebApp (каталог/корзина не переписывались сообщениями бота). **Бот:** `/start` → inline-кнопка `web_app` с `WEBAPP_URL` + постоянная кнопка меню «Магазин»; запуск в `index.ts` (без `BOT_TOKEN` — тихий пропуск). Пользователь создаётся при `/start` по `telegramId`; телефон необязателен (опционально — шаринг контакта). **Фронт:** `telegram-web-app.js` в `index.html`, `initTelegram()` (`ready()`/`expand()`) в `App.vue`, `getInitData()`/`isTelegram()` в `scripts/telegram.ts`; при оформлении `initData` уходит в POST `/orders/create`; в `CartView` — предзаполнение телефона из `GET /users/me` (заголовок `Authorization: tma <initData>`). **Бэкенд:** `verifyInitData` (`@telegram-apps/init-data-node`, HMAC + свежесть) в `global/telegram/initData.ts`; при валидной `initData` — `channel=telegram`, `UserMethods.upsertByTelegram`, `userId` на заказе; поддельная/протухшая — `InvalidInitDataError` (401). E2E-тесты на телеграм-заказ и отклонение фейковой `initData`. Письмо владелице — как в Этапе 2.
  - **Вход в админку из бота (для админов).** В Mini App нельзя ввести адрес руками, поэтому попасть на `/admin` можно только по кнопке из бота.

- **Галерея до 5 картинок.** Форма шлёт multipart с повторяющимся полем `image` (Hono собирает его в массив) — файлы конвертируются в webp (`sharp`) и складываются в `UPLOAD_PATH/images`. - Пути картинок в БД относительные (`images/x.webp`) и раздаются **сервером API**, поэтому на фронте их приводит к абсолютному URL общий хелпер `scripts/images.ts` (`imageUrl`/`imageUrls`) — используется и витриной, и CRM.
- E2E на роут: несколько картинок и их порядок, лимит на создании и обновлении, частичная замена с удалением файла, PATCH без полей картинок, отсев чужого пути, удаление файлов вместе с товаром.

**Заказы — список и статусный флоу.** ✅ Готово.

- **Статусы:** enum `order_status` приведён к `created/paid/assembled/shipped/completed/cancelled`, default `created`. Миграция `0004_order_status_flow.sql` написана вручную поверх сгенерированной: та сразу кастовала колонку в новый enum и упала бы на существующих заказах, поэтому колонка сначала переводится в `text`, старые значения переносятся (`pending→created`, `processing→paid`, `delivered→completed`, `shipped`/`cancelled` как есть) и только потом ставится новый тип.
- **Переходы** — `routes/orders/statusFlow.ts`: только вперёд по цепочке (можно и через шаг — например самовывоз без оплаты), в `cancelled` — с любого места; из `completed` и `cancelled` — никуда. Нарушение → `InvalidStatusTransitionError` (409, `INVALID_STATUS_TRANSITION` с `{from,to}`), неизвестный заказ → `OrderNotFoundError` (404).
- **Сервер:** `GET /orders` (заказ + состав с названиями товаров: два запроса и склейка в `routes/orders/helpers.ts`, без N+1) и `PATCH /orders/:id/status`, оба под `requireAdmin`. Методы: `OrderMethods.getList/getById/updateStatus`, `OrderItemMethods.getByOrderIds`. `PATCH` отвечает в той же форме, что и список (заказ + состав), чтобы клиент мог просто заменить строку ответом.
- **Телеграм покупателя** приезжает join-ом на `users` и отдаётся в CRM полем `telegram: { id, username, name } | null` (у веб-заказов — `null`): по нему владелица пишет клиенту в личку, по `id` уходят уведомления. Плоские `telegram*`-поля join наружу не отдаются.
- **Контакты покупателя:** телефон (`contact`) обязателен, почта (`email`, миграция `0005_order_email.sql`) — необязательна: заполненную проверяем на формат и приводим к нижнему регистру, пустую не сохраняем. Почта видна в карточке заказа (ссылка `mailto:`) и в письме владелице.

Ошибка загрузки показывается вместо списка с «Повторить», ошибка смены статуса — строкой над списком.
- E2E: новый заказ = `created`, список с составом и сортировкой (новые сверху), проход по всей цепочке, запрет шага назад и из завершённого, отмена из середины, неизвестный статус (400) и заказ (404), закрытость от посторонних (401/403).

**Авторизация — только через Telegram.** ✅ Готово. Пароля нет: личность даёт Телеграм, доступ в CRM — только из бота (см. Этап 3), на ПК — через Telegram Desktop.

Режим `popup` — встроенной карте на телефоне (и в Mini App) не хватило бы места.
- **Прокси на сервере** (`routes/cdek/route.ts`): `GET /cdek/service?action=offices` → `deliverypoints`, `POST /cdek/service` с `action=calculate` → `calculator/tarifflist`. Контракт не наш — так виджет ходит в эталонный `service.php` из пакета, поэтому ответ СДЭК пробрасывается как есть, вместе с заголовком `X-Total-Elements` (по нему виджет считает страницы ПВЗ; он же добавлен в `exposeHeaders` CORS — в dev сайт и API на разных портах). Служебный `action` в СДЭК не уходит.
- **Креды только на сервере** (`global/cdek/api.ts`): OAuth-токен `client_credentials` кэшируется на час, на 401 сбрасывается и запрос повторяется один раз; список ПВЗ кэшируется на 10 минут (виджет тянет его страницами при каждом открытии). Ошибка СДЭК наружу отдаётся как 502 `CDEK_API_ERROR` без его текста, ненастроенная интеграция — 503 `CDEK_NOT_CONFIGURED`.
- **Отправитель задаётся кодом города, а не названием** (`CDEK_FROM_CITY_CODE`). Проверено на живом API: `from_location: {code: 270}` возвращает тарифы, а `{address: "Новосибирск"}` — 400, в любом написании и с полным адресом тоже. Виджет, если `from` задан строкой, шлёт именно `{address: ...}`, поэтому цены не считались бы вовсе. Без кода `/cdek/config` отдаёт `enabled: false` — виджет без цен бесполезен. Код ищется разово: `GET /cdek/service?action=cities&country_codes=RU&city=<название>` (действие добавлено только для настройки, виджет его не использует).
- **Настройки — в `.env`, а не в бандле:** `GET /cdek/config` отдаёт клиенту ключ Яндекс.Карт, город-отправитель и габариты упаковки. Менять их можно без пересборки образа (в отличие от `VITE_API_URL`). Нет кредов или ключа карт → `{enabled:false}` → витрина работает как раньше: переключателя нет, покупатель вводит адрес текстом.
- **Посылка считается по составу корзины.** У товара есть свои `weight` (граммы) и `length/width/height` (см в упакованном виде) — миграция `0007_product_parcel.sql`, поля необязательные, в карточке товара в CRM это блок «Посылка». Не заполнено — берётся коробка по умолчанию `CDEK_PARCEL_*` (20×15×10 см, 500 г), так что заполнять можно постепенно.
- **Почему габариты важнее веса:** СДЭК тарифицирует по максимуму из физического и объёмного веса (Д×Ш×В/5000 кг). Вязаная игрушка 25×20×15 см весит 250 г, а по объёму тарифицируется как 1.5 кг — без габаритов расчёт занижался бы на крупных вещах и завышался на мелких.
- **Сборка коробки** (`client/src/scripts/parcel.ts`): одна коробка на заказ (владелица пакует всё вместе, а СДЭК считает по местам). Вес — сумма, объём — сумма; коробка не меньше самого крупного товара, недостающий объём добирается длиной. Коэффициента «на упаковку» намеренно нет: габариты вводятся в упакованном виде, иначе цена завышалась бы на каждом заказе.
- **Изменение корзины сбрасывает выбранную точку** (watch в `stores/cart.ts`): цена доставки посчитана для прежней посылки, оставлять её было бы враньём. Покупатель видит подсказку и выбирает точку заново; если виджет уже был создан, при открытии ему пересобираются `goods` (`resetParcels`/`addParcel`).
- **В заказе** (миграция `0006_order_delivery.sql`): `delivery_method` (`cdek_office` / `cdek_door` / `manual`), `delivery_point_code`, `delivery_tariff_code`, `delivery_price`. Способ и точка видны в CRM и в письме владелице.
- **Стоимость доставки в `totalPrice` не входит** и на сервере не пересчитывается — сохраняем то, что виджет показал покупателю. Пока оплаты нет, это просто справка для владелицы; с подключением оплаты сумму нужно будет считать на сервере (иначе цену доставки можно подделать из браузера).
- E2E (`routes/cdek/cdek.e2e.test.ts`): конфиг включён/выключен, 503 без кредов, 400 на неизвестном действии, проброс ПВЗ с `X-Total-Elements` и кэш, расчёт тарифа с токеном в заголовке, 502 на ошибке СДЭК. Единственное место в тестах, где подменяется внешний сервис (глобальный `fetch`) — ходить в реальный CDEK API из тестов нельзя. В тестах заказов добавлены проверки сохранения ПВЗ и 400 при `cdek_office` без кода точки.
- **Чего ещё нет:** курьерская доставка до двери отдаёт адрес без квартиры (виджет её не спрашивает) — владелица уточняет по телефону; накладная в СДЭК не создаётся, отправка оформляется в ЛК руками.

### Этап 6 (в самом конце) — доставка и оплата

Подключаем после того, как базовый магазин (сайт + почта) работает.

- **Доставка:**
  - **СДЭК** — ✅ сделано, см. блок в «Готово». Осталось: боевые креды интеграции (сейчас всё проверяется на тестовом контуре), ключ Яндекс.Карт под домен магазина и, когда захочется, создание накладной через API (`/orders`) вместо оформления в ЛК руками.
  - **Почта России** — API расчёта тарифа и/или поиска отделений (по аналогии с СДЭК — серверный прокси, креды на сервере). Место в данных уже есть: `delivery_method` — просто текст, добавится ещё одно значение.
  - Вместе с оплатой: считать стоимость доставки на сервере (сейчас сохраняется то, что показал виджет) и включать её в сумму к оплате.
- **Оплата** — сервис пока **не выбран** (кандидаты под самозанятость: ЮKassa / Робокасса / Продамус / ЮMoney, приём по СБП-QR с низкой комиссией). Поля `status`/`paymentMethod` в `orders` уже есть как точка расширения. Требует у владелицы статуса самозанятого + договора с платёжным сервисом.

### Этап 7 — SEO (дизайн зафиксирован; аналитика — отдельно ниже)

Сайт — Vue SPA: до JS в HTML почти нет контента. Яндекс такое индексирует слабо, а краулеры Телеграма/VK/WhatsApp JS **не исполняют** — превью ссылки на товар из лички без серверных мета пустое. Nuxt, `vite-ssg` и предрендер **не берём**: каталог меняется из CRM, статический билд устаревает в тот же день. `@unhead/vue` не подключаем: краулер всегда делает полный запрос, для вкладки браузера хватит `document.title` на карточке.

**Рамки этого этапа:** гигиена + человекочитаемые URL товаров + серверная подстановка HTML. Посадочных страниц категорий нет. Метрика — отдельный кусок (см. ниже).

#### URL

- Карточка: `/product/<slug>`. Ссылки в витрине — на slug. Старый `/product/<uuid>` → **301** на slug, если товар активен; иначе 404.
- Slug у товара как у категории: при создании через `slugify` + суффикс `-2` при коллизии; запасной base, если из названия ничего не вышло — `product`. **При переименовании не меняется.** В CRM slug виден рядом с названием (не редактируется).
- Категории остаются фильтром на главной (`/?category=<slug>`). Отдельного `/category/:slug` нет, в sitemap их нет.

#### Что отдаёт HTML (точка врезки — `serveClientIndex`)

Vue не становится SSR: middleware смотрит путь, читает `index.html`, подставляет head и короткий блок в `#app`, отдаёт его. Браузер монтирует SPA как сейчас.

| Путь                                           | Ответ                                                                                                                     |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `/`                                            | 200, мета магазина                                                                                                        |
| `/?category=…` и любой другой query на главной | 200, `noindex` + `canonical` на `/`                                                                                       |
| `/product/<slug>`                              | 200 + мета товара из БД; нет или `isActive=false` — **HTTP 404** (тело всё равно SPA, чтобы человеку показался экран 404) |
| `/product/<uuid>`                              | 301 на slug, если активен; иначе 404                                                                                      |
| `/product/<slug>?utm=…`                        | 200, `canonical` на чистый URL, **без** `noindex` (метки из чатов не должны выкидывать карточку из индекса)               |
| `/cart`, `/order/*`                            | 200, `noindex`                                                                                                            |
| `/admin`                                       | 200, `noindex` (не HTTP 404 — иначе Mini App админа не откроется; в `robots.txt` путь не упоминать)                       |
| прочий неизвестный путь                        | HTTP 404 + SPA                                                                                                            |

В head: `title`, `description`, `canonical`, OG/Twitter, `theme-color`, на карточке — JSON-LD `Product` (имя, описание, картинки, `Offer`: цена RUB, `InStock` / `OutOfStock` по `stock`, url). Текст из БД экранировать (название/описание товара не должны ломать HTML).

В `#app` — скрытый блок для Яндекса (`h1`, описание, цена, обложка); людям `display: none`, Vue при монтировании его затирает.

`og:image`: у товара — первая фотография галереи; нет фото или главная — файл 1200×630 в `client/public/` (сейчас там только `favicon.jpg`). Абсолютные URL — из `PUBLIC_SITE_URL` в `.env`.

`sitemap.xml` — GET-роут **до** статики: главная + активные товары. Скрытый/удалённый из карты сразу пропадает. `robots.txt` — файл в `client/public/` (`Allow: /`, `Sitemap: …`), без `Disallow: /admin`.

Инъекция работает, когда HTML отдаёт сервер (docker/прод). Vite на `:5173` показывает дефолтные мета из `index.html` — для разработки достаточно.

#### API и витрина

- Колонка `products.slug` (`text`, unique, not null). Миграция с бэкфиллом из названия тем же `slugify`.
- `GET /products/:id` принимает **slug или uuid**. Скрытый товар — **404** (и HTML, и JSON), чтобы старая ссылка не открывала спрятанное. `stock = 0` — карточка живая, в JSON-LD `OutOfStock`. CRM по-прежнему мутирует по uuid; список админки не завязан на этот GET.
- Клиент: роут `/product/:slug`, ссылки с карточки каталога на slug, в ответе API поле `slug`. На странице товара — `document.title` из имени (навигация внутри SPA без перезагрузки).

#### Гигиена (вместе с остальным)

- `<html lang="ru">`, дефолтные `description` / OG / `theme-color` (`#e88630`) в `client/index.html`.
- Шрифты: сейчас в HTML — Google Fonts (Fraunces, Spline Sans, Caveat), локальные Comforter/Noto в `fonts.css` **не те**. Скачать используемые три семейства woff2, `@font-face`, ссылки на `fonts.googleapis.com` убрать. На внешний CDN для РФ-аудитории не завязываемся (доступность + LCP).

#### Компоненты (сервер)

- `global/seo/` — разбор пути, сборка head/блока/JSON-LD, абсолютные URL. Без запросов к БД.
- Методы БД: `ProductMethods.getBySlug`, при создании — тот же `freeSlug`, что у категорий (можно вынести общий хелпер рядом с `slugify`).
- Расширить `serveClientIndex` (или тонкая обёртка рядом): чтение товара, 301/404, подстановка. `sitemap.xml` — `routes/seo/` (или рядом со статикой), не файл в `public/`.
- Плейсхолнеры в `index.html` (`<!--seo-head-->`, слот в `#app`), чтобы подстановка была предсказуемой, а не regex по всему файлу.

#### Ошибки и кэш

- Нет `PUBLIC_SITE_URL` — предупреждение в лог, относительные URL лучше не выдумывать для OG (превью без абсолютного `og:image` сломается); в проде переменная обязательна.
- HTML витрины по-прежнему `Cache-Control: no-cache`. Sitemap — короткий кэш (порядка часа).
- Сбой чтения БД на инъекции не должен ронять процесс: отдать `index.html` с дефолтными мета (как сейчас) и залогировать.

#### Тесты (E2E)

- HTML `/product/<slug>`: 200, title/h1/цена/JSON-LD/`og:image` из обложки; скрытый и несуществующий — 404.
- `/product/<uuid>` активного — 301 на slug; скрытого — 404.
- `GET /products/<slug>` и `GET /products/<uuid>` — тот же JSON; скрытый — 404.
- POST создаёт slug, коллизия даёт `-2`, PATCH имени slug не меняет.
- `GET /sitemap.xml` — главная + активные, без скрытых.
- `/` с `?category=` — `noindex` и canonical на `/`; `/product/slug?utm=` — canonical без noindex.
- `/admin`, `/cart` — заголовок `X-Robots-Tag: noindex`.

После деплоя — сайт в Яндекс.Вебмастер и Google Search Console, отправить sitemap.

**Порядок работ внутри SEO:** миграция slug → API/витрина на `/product/:slug` → гигиена `index.html`/шрифты/`robots.txt`/og-картинка → инъекция + sitemap. Без slug подставлять нечего в canonical.

**Аналитика посещаемости** (не в этом этапе). **Яндекс.Метрика** по умолчанию (бесплатно, вебвизор и тепловые карты, хорошо работает в РФ). Umami/Plausible — это ещё контейнер и домен, для одного магазина не стоит; GA4 в РФ хуже с доступностью. Счётчик подключать через `VITE_YM_ID` (пусто в dev — не грузится).

- Нюанс SPA: считать не только первый заход, а **смену роутов** — отправка «просмотра» на `router.afterEach`, иначе переходы внутри сайта не учитываются.
- Нюанс Mini App: заходы из Телеграма — тот же сайт в WebView, без referrer, и в отчётах сольются с «прямыми заходами». Помечать канал через готовый `isTelegram()` (`client/src/scripts/telegram.ts`) — параметром визита или отдельным счётчиком.
- **Предварительная доработка для цели «покупка»:** `OrderSuccessView` не знает ни id заказа, ни суммы — корзина к этому моменту уже очищена. Чтобы отправлять ecommerce-`purchase`, а не просто «просмотр страницы спасибо», надо прокинуть ответ `POST /orders/create` в success-view (router state или стор).

### Технический долг (не блокирует, но пусть будет записано)

- **Корневой `bunx tsc --noEmit` не является гейтом** — даёт ~98 ошибок и без наших правок: не понимает bun-специфичные `@global/*` из `server/package.json`, не подхватывает `@types/bun` (`Bun.file`, `import.meta.dir`) и заодно тянет клиент с его алиасами. Проверка — тесты (`bun test`) и `type-check` в клиенте. Если захочется настоящей проверки типов по серверу — отдельный `tsconfig` в `server/` с `types: ["bun"]` и `paths` под `@global/*`.
- **`data/mongodb/`** — наследие Mongo до Этапа 1. В образ не попадает (`.dockerignore`), можно удалить.
- **CORS фактически не нужен:** сайт и API на одном домене. `CORS_ORIGINS` остаётся для dev-браузера на 5173.
- **Порядок картинок у товара** меняется только удалением и повторной загрузкой (сервер произвольный порядок принимает — не хватает лишь стрелок в форме).

## Безопасность перед публикацией

- Перевыпустить `BOT_TOKEN` у @BotFather и сменить пароль БД (старые были в git-истории).
- `.env` не коммитить; Postgres наружу не публиковать в проде (в dev порт 15432 открыт намеренно); домен + SSL.
- **`ADMIN_AUTH_DISABLED` в проде не задавать** — переменная снимает проверку прав со всех мутирующих эндпоинтов (нужна только для CRM в браузере на localhost).
- `ADMIN_TELEGRAM_IDS` — только свой id; `ADMIN_JWT_SECRET` задать отдельным значением (иначе сессии подписываются `BOT_TOKEN` и умирают при его перевыпуске); `CORS_ORIGINS` — только домен магазина.
- **Образ собирать с прод-адресом:** `VITE_API_URL=https://<домен> docker compose build`. Адрес API вшивается в бандл на сборке — при смене домена образ надо пересобрать, перезапуск не поможет.
- **`PUBLIC_SITE_URL`** — абсолютный адрес магазина без хвоста (`https://shop.example.com`). Нужен для `canonical`, `og:image` и sitemap; без него превью ссылок в мессенджерах не соберётся.
- **В бэкап включить оба тома:** `pgdata` (база) и `uploads` (картинки товаров) — картинок в git нет, и восстановить их будет неоткуда.
