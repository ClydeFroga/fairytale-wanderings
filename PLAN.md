# План — fairytale-wanderings

Магазин подруги: каталог + заказы. Цель — убрать трение «напиши в личку и перечисли заказ руками»: клиент собирает заказ сам (сайт — гостевой checkout; тот же сайт открывается внутри Телеграма как Mini App — для удобства), заказ уходит владелице и сохраняется в БД.

Стек: Vue 3 (клиент) + Hono/Bun + PostgreSQL/Drizzle (сервер), docker-compose. Подробности по серверу — в `server/CLAUDE.md`.

## Готово ✅

- **Зависимости** обновлены до последних (Vue 3.5, Vite 8, ESLint 10, Hono 4.12, zod 4, TS 6 и т.д.). Mongoose оставлен на 8.x и затем убран при миграции.
- **Этап 1 — миграция БД Mongo → PostgreSQL + Drizzle.** Схема по файлам в `server/src/global/database/shema/` (products, users, orders, order_items + enum-ы). Пул и drizzle — в `DatabaseSingleton` (экспортирует `db`). Миграции через drizzle-kit (`server/drizzle/`). Compose переведён на postgres (порт на хосте — **15432**, наружу через `POSTGRES_PORT`).
- **Этап 2 — запись заказа в БД + письмо владелице.** У товара есть `stock`; при заказе остаток списывается атомарно (`stock >= qty`), при нехватке — `InsufficientStockError` (409, со списком всех недостающих позиций в `details.shortages`), нет товара — `ProductNotFoundError` (404). Ошибки `AppError` отдаются как JSON `{ error, code, details }`. Цена фиксируется из БД. Сохраняются имя и контакт. Гостевой checkout (без регистрации), `userId = null`. После успешной записи заказа владелице уходит письмо по SMTP (`nodemailer`, модуль `server/src/global/mail/`): состав, суммы, контакт, доставка. Креды в `.env` (`SMTP_`\*, `MAIL_FROM/TO`); если не заданы — письмо тихо пропускается, заказ всё равно создаётся.
- **Структура и конвенции** (см. `server/CLAUDE.md`): бизнес-логика — в роутах; `database/methods/` — только обращения к БД (импортируют `db` напрямую); ошибки — в `global/errors/` (`AppError` + наследники со `status`); единый обработчик — `middleware/errorHandler.ts` через `app.onError`. Роуты разложены по папкам (`routes/<name>/route.ts|validator.ts|helpers.ts`).
- **Seed**: 5 тестовых товаров с остатками (`bun run db:seed`).
- **Этап 3 — Telegram Mini App.** Сайт открывается внутри Телеграма как WebApp (каталог/корзина не переписывались сообщениями бота). **Бот:** `/start` → inline-кнопка `web_app` с `WEBAPP_URL` + постоянная кнопка меню «Магазин»; запуск в `index.ts` (без `BOT_TOKEN` — тихий пропуск). Пользователь создаётся при `/start` по `telegramId`; телефон необязателен (опционально — шаринг контакта). **Фронт:** `telegram-web-app.js` в `index.html`, `initTelegram()` (`ready()`/`expand()`) в `App.vue`, `getInitData()`/`isTelegram()` в `scripts/telegram.ts`; при оформлении `initData` уходит в POST `/orders/create`; в `CartView` — предзаполнение телефона из `GET /users/me` (заголовок `Authorization: tma <initData>`). **Бэкенд:** `verifyInitData` (`@telegram-apps/init-data-node`, HMAC + свежесть) в `global/telegram/initData.ts`; при валидной `initData` — `channel=telegram`, `UserMethods.upsertByTelegram`, `userId` на заказе; поддельная/протухшая — `InvalidInitDataError` (401). E2E-тесты на телеграм-заказ и отклонение фейковой `initData`. Письмо владелице — как в Этапе 2.
  - **Вход в админку из бота (для админов).** В Mini App нельзя ввести адрес руками, поэтому попасть на `/admin` можно только по кнопке из бота.
    - **Кто админ:** `ADMIN_TELEGRAM_IDS` в `.env` (telegramId через запятую; свой id — у `@userinfobot`) **или** флаг `users.is_admin` в БД. Единая проверка — `isAdmin(telegramId, dbUser)` в `global/telegram/admins.ts`; права всегда считаются по telegramId из проверенной `initData` (или из апдейта бота), не по данным клиента.
    - **Бот:** в ответе на `/start` админу добавляется вторая inline-кнопка «Панель управления» — то же Mini App, но открытое сразу на `WEBAPP_URL/admin` (URL-ы собирает `global/telegram/webAppUrl.ts`); плюс в его чат прописывается команда `/admin` (`setMyCommands` со `scope: chat`), чтобы кнопка не терялась в истории. `AdminListener` на `/admin` шлёт ту же кнопку; не-админам команда **молчит** — раздел не афишируем (как 404 на фронте). Общая меню-кнопка у поля ввода остаётся «Магазин» для всех.
    - **Фронт/API:** `GET /users/me` отдаёт `isAdmin` по тому же правилу — на нём уже стоит гард `requireAdmin` роута `/admin` (не админ → 404, в dev проверка отключена). E2E: обычный пользователь, админ по `.env`, админ по флагу в БД.
    - **Нюанс деплоя:** сервер (или прокси) должен отдавать `index.html` на `/admin` — иначе Mini App откроется в 404 сервера. Сам доступ к API админки пока не закрыт — это Этап 5.

### Этап 5 — CRM (админка владелицы) — ✅ готово (кроме опт-ина уведомлений для веб-заказов)

Закрытая панель управления (`/admin` → `AdminLayout` → `CRMView`, вход — кнопкой из бота, см. Этап 3). Разделы: товары, категории, заказы (`components/crm/`). Мутирующие эндпоинты закрыты `requireAdmin` (см. блок про авторизацию).

**Товары — CRUD.** ✅ Готово. Список (`ProductsPanel`), форма-шторка создания/редактирования (`ProductFormDrawer`), удаление с подтверждением; данные — через `stores/products.ts` → `api/products.ts` → `GET/POST/PATCH/DELETE /products`.

- **Галерея до 5 картинок.** Форма шлёт multipart с повторяющимся полем `image` (Hono собирает его в массив) — файлы конвертируются в webp (`sharp`) и складываются в `UPLOAD_PATH/images`. Лимит — `MAX_PRODUCT_IMAGES = 5` (в `routes/products/validator.ts` и `api/products.ts`), превышение → `TooManyImagesError` (400, `TOO_MANY_IMAGES`), нечитаемый файл → `InvalidImageError` (400).
- **Правка галереи:** `PATCH` принимает `existingImages` — JSON-массив путей, которые остаются у товара (в нужном порядке); итог = оставленные + новые файлы. Поле не пришло — галерея не трогается. Чужие пути отбрасываются (клиент не может записать в товар произвольный файл).
- **Файлы на диске** чистятся: выпавшие из товара при `PATCH`, все при `DELETE`, только что залитые — при откате неудачного запроса (`Upload.saveImages`/`Upload.removeMany`, старый `utils/deleteFile.ts` удалён).
- **Обложка** — первая картинка (в форме помечена, в списке — счётчик картинок). Перетаскивания/смены порядка нет: чтобы сменить обложку, картинку надо убрать и загрузить заново. Если станет неудобно — добавить стрелки порядка (сервер уже принимает произвольный порядок в `existingImages`).
- Пути картинок в БД относительные (`images/x.webp`) и раздаются **сервером API**, поэтому на фронте их приводит к абсолютному URL общий хелпер `scripts/images.ts` (`imageUrl`/`imageUrls`) — используется и витриной, и CRM.
- E2E на роут: несколько картинок и их порядок, лимит на создании и обновлении, частичная замена с удалением файла, PATCH без полей картинок, отсев чужого пути, удаление файлов вместе с товаром.

**Категории — CRUD.** ✅ Готово. `CategoriesPanel` работает с БД: `GET/POST/PATCH/DELETE /categories` через `api/categories.ts` → `stores/categories.ts` (локальный демо-список строк удалён, форма товара берёт категории из того же стора).

- **Slug** генерируется на сервере из названия транслитом (`global/utils/slugify.ts`: «Вязаные игрушки» → `vyazanye-igrushki`), при совпадении транслитерации — суффикс `-2`. **При переименовании slug не меняется** — на него завязаны ссылки витрины (`/?category=<slug>`); в списке он показан рядом с названием, чтобы это было видно.
- Дубль названия (без учёта регистра) → `DuplicateCategoryError` (409, `DUPLICATE_CATEGORY`), неизвестный id → `CategoryNotFoundError` (404). На клиенте кнопка «Добавить» гаснет до запроса.
- Новая категория получает `sortOrder = max + 1` (это порядок вкладок на витрине). Ручной перестановки в UI нет — поле сервер принимает, если понадобится.
- **Удаление** не удаляет товары: у них обнуляется `categoryId` (FK `ON DELETE SET NULL`). В подтверждении сказано, сколько товаров станет «без категории», после удаления список товаров перечитывается.
- Переименование — инлайн в строке списка; счётчик товаров у категории считается по `categoryId`.
- E2E: транслит slug, суффикс при коллизии, дубли при создании и переименовании, 400 на пустом названии, 404 на неизвестном id, удаление с проверкой, что товары остались в каталоге без категории.

**Заказы — список и статусный флоу.** ✅ Готово.

- **Статусы:** enum `order_status` приведён к `created/paid/assembled/shipped/completed/cancelled`, default `created`. Миграция `0004_order_status_flow.sql` написана вручную поверх сгенерированной: та сразу кастовала колонку в новый enum и упала бы на существующих заказах, поэтому колонка сначала переводится в `text`, старые значения переносятся (`pending→created`, `processing→paid`, `delivered→completed`, `shipped`/`cancelled` как есть) и только потом ставится новый тип.
- **Переходы** — `routes/orders/statusFlow.ts`: только вперёд по цепочке (можно и через шаг — например самовывоз без оплаты), в `cancelled` — с любого места; из `completed` и `cancelled` — никуда. Нарушение → `InvalidStatusTransitionError` (409, `INVALID_STATUS_TRANSITION` с `{from,to}`), неизвестный заказ → `OrderNotFoundError` (404).
- **Сервер:** `GET /orders` (заказ + состав с названиями товаров: два запроса и склейка в `routes/orders/helpers.ts`, без N+1) и `PATCH /orders/:id/status`, оба под `requireAdmin`. Методы: `OrderMethods.getList/getById/updateStatus`, `OrderItemMethods.getByOrderIds`. `PATCH` отвечает в той же форме, что и список (заказ + состав), чтобы клиент мог просто заменить строку ответом.
- **Телеграм покупателя** приезжает join-ом на `users` и отдаётся в CRM полем `telegram: { id, username, name } | null` (у веб-заказов — `null`): по нему владелица пишет клиенту в личку, по `id` уходят уведомления. Плоские `telegram*`-поля join наружу не отдаются.
- **Контакты покупателя:** телефон (`contact`) обязателен, почта (`email`, миграция `0005_order_email.sql`) — необязательна: заполненную проверяем на формат и приводим к нижнему регистру, пустую не сохраняем. Почта видна в карточке заказа (ссылка `mailto:`) и в письме владелице.
- **Фронт:** `api/orders.ts` (`getOrders`/`updateOrderStatus`), `stores/orders.ts` на реальных данных (демо-заказы удалены), `OrdersPanel` показывает номер, клиента с контактом, ссылку `@username` на личку (или `tg id`, если username не задан), состав, адрес, сумму, канал (сайт/Telegram) и полосу этапов; кнопка следующего статуса и «Отменить» с подтверждением. Ошибка загрузки показывается вместо списка с «Повторить», ошибка смены статуса — строкой над списком.
- E2E: новый заказ = `created`, список с составом и сортировкой (новые сверху), проход по всей цепочке, запрет шага назад и из завершённого, отмена из середины, неизвестный статус (400) и заказ (404), закрытость от посторонних (401/403).
- `оплачен`: после интеграции оплаты (Этап 6) статус будет выставляться автоматически по факту платежа; до этого — вручную из CRM.

**Уведомления клиенту в Telegram (на смену статуса).** ✅ Готово для телеграм-заказов. Ограничение Телеграма: бот пишет только тем, кто с ним уже связан, и только по `chat_id`.

- **Авто (телеграм-заказы):** каждая смена статуса в `PATCH /orders/:id/status` шлёт клиенту короткое сообщение по `users.telegramId` (шаблоны на оплачен/собран/отправлен/завершён/отменён — `global/notify/orderNotify.ts`; «создан» уходит при оформлении заказа). Модуль по образцу `global/mail/`: ленивый `Telegram` из telegraf по `BOT_TOKEN`, **без поллинга бота**. Best-effort: нет токена, клиент заблокировал бота, сеть — ошибка логируется, статус меняется всё равно.
- **Опт-ин для веб-заказов — отложен (решение).** У браузерного гостя нет `chat_id`, поэтому на экране «Заказ принят» пока ничего не показываем. Когда понадобится: кнопка «Получать статусы в Telegram» → deep-link `t.me/<бот>?start=order_<id>` → обработка `start_param` в `StartListener` + nullable `notify_telegram_id` на `orders` (потребует миграции).

**Авторизация — только через Telegram.** ✅ Готово. Пароля нет: личность даёт Телеграм, доступ в CRM — только из бота (см. Этап 3), на ПК — через Telegram Desktop.

- **Вход:** `POST /auth/login` с `Authorization: tma <initData>` — сервер проверяет подпись и свежесть `initData`, сверяет права через `isAdmin()` и ставит подписанную httpOnly-куку `admin_session` (`hono/jwt`, HS256, 12 часов; секрет — `ADMIN_JWT_SECRET`, иначе `BOT_TOKEN`; модуль `global/auth/adminSession.ts`). Кука нужна потому, что `initData` живёт час и не обновляется, пока Mini App открыт. `POST /auth/logout` сбрасывает куку (UI-кнопки нет — внутри Mini App повторный вход всё равно происходит автоматически).
- **Защита:** middleware `requireAdmin` (`middleware/requireAdmin.ts`) на `POST/PATCH/DELETE /products` и `POST/PATCH/DELETE /categories`. Пускает по куке **или** по свежей админской `initData` в заголовке — второй путь нужен для первого запроса и как запас, если WebView блокирует сторонние куки. Ни того, ни другого → 401 `UNAUTHORIZED`; личность есть, но не админ → 403 `FORBIDDEN`. Чтение (`GET /products`, `GET /categories`) открыто — это витрина.
- **Фронт:** гард роута `/admin` вызывает `POST /auth/login` (`api/auth.ts`) — это одновременно проверка прав и получение куки; `apiClient` шлёт `credentials: 'include'` и внутри Телеграма сам подставляет `Authorization: tma <initData>` во все запросы.
- **Dev:** в браузере вне Телеграма `initData` взять негде — фронт пропускает гард по `import.meta.env.DEV`, сервер — по `ADMIN_AUTH_DISABLED=true` (стоит в `.env.development`, в проде не ставить; в тестах переменная принудительно сбрасывается).
- **CORS:** домены фронта задаются `CORS_ORIGINS` через запятую (с `credentials: true` нельзя `*`), в `allowMethods` добавлен пропущенный ранее `PATCH` — без него правка товара/категории из браузера не проходила preflight.
- E2E (`routes/auth/auth.e2e.test.ts`): логин админа (кука `HttpOnly`), не админ → 403, поддельная и отсутствующая `initData` → 401, кука вместо `initData` на защищённом роуте, битая кука → 401, `logout`. В тестах товаров и категорий добавлены проверки 401 (без авторизации) и 403 (не админ), остальные мутации ходят с админскими заголовками (`test/e2e/auth.ts`).
- Осталось навесить `requireAdmin` на `GET /orders` и `PATCH /orders/:id/status`, когда появятся сами роуты (см. блок про заказы).

### Этап 6 (в самом конце) — доставка и оплата

Подключаем после того, как базовый магазин (сайт + почта) работает.

- **Доставка:**

- **Оплата** — сервис пока **не выбран** (кандидаты под самозанятость: ЮKassa / Робокасса / Продамус / ЮMoney, приём по СБП-QR с низкой комиссией). Поля `status`/`paymentMethod` в `orders` уже есть как точка расширения. Требует у владелицы статуса самозанятого + договора с платёжным сервисом.

### Этап 7 — SEO и аналитика (можно делать независимо)

**SEO.** Важный нюанс: сайт — это client-rendered Vue SPA (Vite), а такие страницы поисковики (особенно Яндекс) индексируют плохо — в HTML почти нет контента до выполнения JS. Поэтому:

- **База (дёшево):** мета-теги на каждый роут (`@unhead/vue` или `@vueuse/head`) — `title`, `description`, OG/Twitter-карточки; `canonical`; `robots.txt`; `sitemap.xml`; JSON-LD `Product` на страницах товара (цена, наличие — для красивых сниппетов). URL уже человекочитаемые (`/product/:id`), при желании — slug вместо id.
- **Главный рычаг:** предрендеринг страниц в статический HTML на сборке (`vite-ssg` или плагин предрендера) — тогда у поисковика и соцсетей есть готовый контент. Полноценный SSR (миграция на Nuxt) — избыточно для этого магазина, не берём.
- После деплоя — добавить сайт в Яндекс.Вебмастер и Google Search Console, отправить sitemap.

**Аналитика посещаемости.** Для РФ-аудитории — **Яндекс.Метрика** (бесплатно, вебвизор и тепловые карты, хорошо работает в РФ). Альтернатива с упором на приватность и self-host — **Umami** или Plausible (можно поднять контейнером в docker-compose, без cookie-баннера). GA4 — глобальный вариант, но в РФ хуже с доступностью/приватностью. Рекомендация: Метрика по умолчанию, Umami — если хочется свой инстанс.

- Нюанс SPA: считать не только первый заход, а **смену роутов** — вешать отправку «просмотра» на `router.afterEach`, иначе переходы внутри сайта не учитываются.

## Безопасность перед публикацией

- Перевыпустить `BOT_TOKEN` у @BotFather и сменить пароль БД (старые были в git-истории).
- `.env` не коммитить; Postgres наружу не публиковать в проде (в dev порт 15432 открыт намеренно); домен + SSL.
- **`ADMIN_AUTH_DISABLED` в проде не задавать** — переменная снимает проверку прав со всех мутирующих эндпоинтов (нужна только для CRM в браузере на localhost).
- `ADMIN_TELEGRAM_IDS` — только свой id; `ADMIN_JWT_SECRET` задать отдельным значением (иначе сессии подписываются `BOT_TOKEN` и умирают при его перевыпуске); `CORS_ORIGINS` — только домен магазина.
